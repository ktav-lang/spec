# Review: spec 0.8.0 leading-zero rule (§ 5.2 rules 13–14) — pre-tag audit

Reviewed: spec `0a70ce4`, rust `49f044d` + `092d55c`. Read-only; the only file written is this report.
A throwaway probe example (`rust/examples/lz_probe_tmp.rs`) was compiled, run and deleted; `git status` in `rust/` is clean.

## Verdict

**Not safe to tag as-is.** The normative rule itself (§ 5.2 rules 13–14), the two new `valid/` fixtures, the 13 remaining `strict-lossy/` fixtures, the manifest counts, the corpus inventory lock, the build `--check`, and the Rust implementation (all four classification sites) are consistent with each other and with the stated definition — I found no behavioural bug and no divergence between implementation and rule. What is broken is the spec's own self-description: **Appendix A's 0.8.0 entry still states, in all three languages, that the lax entry point is unchanged and every canonical rendering is byte-identical to 0.7.x** — the exact opposite of the release's headline change — and § 8.1 still uses `01234 → 1234` as its worked example of a lossy scalar. Both are in generated `spec*.md` and in their unit sources, so they are not build artefacts. Fix those two (blocker + major), then the § 5.9.6 "exactly one branch applies" gap (major), and the tag is defensible. The Rust crate additionally cannot ship this change as `0.7.2` under its own stated convention.

## CONFIRMED findings

### 1. Appendix A 0.8.0 entry contradicts the release (blocker)

`versions/0.8/spec.md:3346-3350`:

> ### 0.8.0 — 2026-09-19
>
> No change to the lax entry point (`parse`/`loads`): every document that parsed under 0.7.x parses to the same Value under 0.8.0, and every canonical rendering is unchanged byte for byte.

Same text in `versions/0.8/spec.ru.md:3546-3550` ("Нестрогая точка входа (`parse`/`loads`) не меняется … побайтово прежней") and `versions/0.8/spec.zh.md:2703-2706` ("宽松入口(`parse`/`loads`)不变 … 逐字节不变"). Source unit: `versions/0.8/content/releases/sec-0.8.0/body-1.md:1-5, 27-30, 51-53`.

The entry's only bullets are "§ 8.1 — new obligation" and "Appendix E — new". There is no § 5.2 bullet. Every prior breaking change in Appendix A (0.7.0, 0.5.0) carries an explicit "**Breaking:**" bullet. The root CHANGELOG (`root-docs/CHANGELOG/v0.8.0/body-1.md`) and Appendix E were rewritten (commit message says so); Appendix A was not. The two documents now disagree about the central fact of the release.

Concrete failing input: `zip: 01234` — 0.7.x Value `Integer(1234)`, canonical `zip: 1234`; 0.8.0 Value `String("01234")`, canonical `zip:: 01234`. Both "same Value" and "unchanged byte for byte" are false.

Fix: rewrite `content/releases/sec-0.8.0/body-1.md` (all three blocks) to drop the "No change" paragraph, add a "**Breaking:** § 5.2 — …" bullet mirroring the root CHANGELOG's wording, then rebuild (`node scripts/build_spec.mjs`) so all three `spec*.md` regenerate.

### 2. § 8.1 still uses `01234 → 1234` as the lossy example (major)

`versions/0.8/spec.md:2937-2941`:

> A fixture is *lossy* when its lexical form differs from the canonical form of the number § 5's rules 13–14 infer from it (`1.10` → `1.1`, `01234` → `1234`, `0x1A2B` → `6699`, …)

Source: `versions/0.8/content/practice/compliance/sec-8.1/body-3.md:61-62` (en), `:132` (ru: "`01234` → `1234`"), `:188` (zh: "`01234` → `1234`"). Rules 13–14 infer no number from `01234` under 0.8, so this example is not merely stale — it asserts a classification § 5.2 forbids. A reader implementing strict mode from § 8.1 alone would report `LossyScalar` for `01234`, which the `valid/` fixture now rejects.

Fix: replace `01234` → `1234` with a still-lossy example, e.g. `+7` → `7` or `1_000` → `1000`, in all three blocks.

Related, pre-existing but worth noting while touching § 8.1: `spec.md` still cites `versions/0.7/tests/…` in 15 places (`spec.md:676, 1741-1742, 2887, 2903, 2929, 2932, 2938, 2958, 2962, 2978, 2992, 3031, 3033`) and says "0.7.0-conformant parser" at `:926, :958, :3534`. `versions/0.7/tests/` has no `strict-lossy/` directory at all, so § 8.1's "for every fixture under `versions/0.7/tests/strict-lossy/`" (`:2937-2938`) names a path that does not exist. Not introduced by this change, but 0.8's own § 8.1 obligation is currently pointed at a corpus that cannot satisfy it.

### 3. § 5.9.6 raw-marker item branch no longer covers a leading-zero String (major)

`versions/0.8/spec.md:1955-1956`: "The writer MUST test the following branches in order; exactly one branch applies".

Bare String item branch (`:1965-1967`): "when the body satisfies the same conditions as the `key: <bytes>` form of § 5.9.5" — § 5.9.5 (d) (`:1908-1911`) requires the body "does not match the integer or float literal grammar of § 3.6". `01234` matches the grammar → bare branch excluded. Correct and intended.

Raw-marker item branch (`:2008-2016`): "This branch applies only when the body is a physically safe non-empty one-line String … The body would otherwise be reinterpreted by § 5.2 as a number, keyword, an inline compound, …". Under 0.8, `01234` emitted bare is **not** reinterpreted by § 5.2 as a number — § 5.2 rule 13 sends it to rule 15, String. So the raw-marker branch's stated condition is false for it. Neither branch applies; "exactly one branch applies" is violated for `String("01234")` in array-item position.

Contrast § 5.9.5's raw-marker pair branch (`:1934-1939`), which is phrased "would otherwise be reinterpreted by § 5.2 if emitted with plain `:` — either as matching the integer or float literal grammar of § 3.6 (regardless of whether the value fits the writer's own numeric domain)" — the parenthetical makes grammar-match the operative criterion, so the pair case still resolves. § 5.9.6 has no such parenthetical: it says only "as a number".

Concrete input: Value `Array[String("01234")]`. Rust emits `:: 01234\n` (probe, and `render/helpers.rs:407-410` keys off `matches_integer_grammar`). That is the right output; the text just does not say so.

Fix: in `content/language/semantics/9/sec-5.9.6/body-3.md:58` (and ru/zh blocks) change "as a number" to "as matching the integer or float literal grammar of § 3.6 (regardless of § 5.2's redundant-leading-zero exception or the writer's numeric domain)" — i.e. the same wording § 5.9.5 already has. Optionally add one sentence to § 5.9.5/§ 5.9.6 stating explicitly that a String such as `01234`, which § 5.2 would keep a String, still takes the raw marker because the writer's criterion is the grammar, so that the marker choice is domain- and rule-independent.

Idempotence / round-trip / minimality: verified, NOT A PROBLEM. Probe: `emit_canonical(parse(canon)) == canon` and `parse(canon) == parse(doc)` for `k: 01234`, `k:: 01234`, multi-line `01234`, `[01234]`, `{z: 01234}`, `k: {a: 01234, b: 0_7}`, bare item `01234`, root array `01234`. § 5.9 (`spec.md:1644-1666`) and § 10.6 (`:3248-3270`) claim byte-determinism, not minimality; no "shortest" claim exists for Strings. `zip:: 01234` vs `zip: 01234` both re-read to the same Value, so canonical form is now not the *only* faithful spelling — but nothing in § 5.9 promises that.

### 4. Rust crate version / changelog (major)

`rust/Cargo.toml:3`: `version = "0.7.2"`. `rust/CHANGELOG.md:7-8`: "this crate adheres to Semantic Versioning with the Cargo convention that a minor bump is breaking while pre-1.0". `rust/CHANGELOG.md:13-18` (`## [0.7.2] — unreleased`): "the release is purely additive to the public API". No line in `rust/CHANGELOG.md` mentions the leading-zero change (grep for `leading zero|01234` hits only the 0.6.2 entry at `:373`, which itself still says `01234` → `1234`).

`parse("zip: 01234")` returning a different `Value` variant is an observable behavioural break of the public API. Under the crate's own convention it requires `0.8.0`, and the spec-conformance target moving from 0.7 to 0.8 (`tests/spec_conformance/support.rs:11`, `SPEC_VERSION = "0.8"`) is the natural reason to align the crate at 0.8.0.

Risk if shipped as 0.7.2: `golang/Cargo.toml:13`, `java/Cargo.toml:13` (and the js/php/python/csharp workspaces on the same template) declare `ktav = "0.7.2"`, a caret requirement satisfied by any 0.7.x. Every binding silently changes the type of `01234` on its next `cargo update`, while its spec submodule (v0.7.1) and its README (`zip:: 01007` advice) still describe the old behaviour. A `0.8.0` bump makes the pickup an explicit act.

### 5. Rust CI does not run the 0.8 corpus (major, release-readiness)

`rust/.gitmodules` pins `spec/`; `git submodule status` → `adec268 spec (v0.7.1)`. `tests/spec_conformance/support.rs:21-28`:

> // Require THIS version's directory specifically … the `spec` submodule stays pinned to an older tag between spec releases (currently v0.7.1, no `versions/0.8`), so a generic check would resolve to a root that then fails § 8.5 enforcement below instead of gracefully skipping the suite.

Candidates are `KTAV_SPEC_DIR`, `spec/`, `../spec`. On this machine `../spec` = `D:/dev/ktav-lang/spec` and the suite runs (I ran `cargo test --test spec_conformance --test strict_mode --test readme_strict_snippet`: 1 + 12 + 9 passed). On a clean clone or in CI, the suite returns `None` and skips silently; the commit message's "only the corpus found the third site" happened via the sibling checkout, not via anything CI sees. After tagging spec 0.8.0 the submodule must be bumped in the same rust release, or the strict-lossy runner and the two new fixtures are unverified in CI.

### 7. § 5.9.5 rationale and `render/helpers.rs` doc comment (minor)

`spec.md:1934-1936`: "`key:: <bytes>` … that would otherwise be reinterpreted by § 5.2 if emitted with plain `:` — either as matching the integer or float literal grammar". The "would otherwise be reinterpreted by § 5.2" clause is false for `01234`; the grammar-match parenthetical is what saves the branch. `rust/src/render/helpers.rs:382-385`: "True if the value must be emitted with `::` so that the parser does not re-interpret it as … a number literal (§ 3.6)" — same stale justification (the predicate's own doc at `classify.rs:237-240` states the real reason correctly). ### 8. Root README never mentions the exception and uses `01007` as the "force it" example (minor)

`spec/README.md:338-340` (source `root-docs/README/the-rules-in-one-screen/body-5.md:13, 42, 65`): "To keep a numeric-looking value as text regardless of size, force it with `::` (`zip:: 01007`)." Under 0.8, `zip: 01007` is already the String. The advice is not wrong (canonical form still emits `zip:: 01007`), but it is the one example that now teaches the opposite of the release's point, and the "rules in one screen" section does not state the leading-zero exception anywhere. Suggest changing the example to a value that genuinely needs forcing (e.g. `id:: 1234` or `ver:: 1.10`) and adding one line for the exception.

### 9. Exponent-leading-zero and `0e3` are unstated and unexercised (minor)

Rule 14 text (`spec.md:963-966`) scopes the exception to "the digits before the decimal point — or before the exponent in the point-less alternative". By construction the exponent's `dec_part` and the fractional `dec_part` are outside scope, so `1e01`, `1.5e01`, `1.05` are Floats. Rust agrees: probe → `1e01` = `Float(10.0)` / strict `Lossy(1e01->10.0)`; `1.5e01` = `Float(15.0)`; `0e3` = `Float(0.0)` / strict `Lossy(0e3->0.0)`; `0e01` = `Float(0.0)`. This is what the text intends and it is unambiguous, but no example in the text and no fixture in `valid/` or `strict-lossy/` pins it; the only exponent fixture is `strict-lossy/float/exponent` (`5e3`). An implementer who reads "redundant leading zero" loosely and applies it to the exponent run would pass the whole corpus. Add `1e01` (Float, lossy → `10.0`) and `0e3` (Float `0.0`) to the float fixture or to `strict-lossy/`, and one clause in rule 14 saying the exponent digits are never in scope.

### 10. Appendix E migration regex (nit)

## Checked and found fine (coverage)

- **§ 5.2 rules 13–14 definition vs implementation.** `has_redundant_leading_zero` (`rust/src/parser/syntax/classify.rs:241-252`): optional sign, then `0`, then a digit or `_`. Matches "first digit 0, at least one further digit, sign and underscores ignored". The `_` case fires on grammar-invalid `0_`/`0__1`/`0_x1`, but those are Strings under rule 15 anyway, so the observable result is identical. Probe results (lax / strict / inline `[…]` / thin events / canonical), all four sites agreeing:
  `0_`→S, `00x1`→S, `+0`→I(0)/Lossy, `-0`→I(0)/Lossy, `0x0`→I(0)/Lossy, `0.5`→F, `0e3`→F(0.0)/Lossy, `01e3`→S, `0__1`→S, `0_7`→S, `00`→S, `-045`→S, `01234`→S, `0.0`→F, `00.5`→S, `0_0.5`→S, `-01.5`→S, `+01.5`→S, `1e01`→F(10.0)/Lossy, `1.5e01`→F(15.0)/Lossy, `0`→I, `+01`→S, `0e01`→F, `0.05`→F, `1.05`→F, `-0.0`→F(-0.0), `0E3`→F/Lossy, `00e3`→S, `0_1e3`→S, `0b0`/`0o0`/`0x00`→I(0)/Lossy.
